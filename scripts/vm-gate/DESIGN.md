# vm-gate dispatcher design

Goal 1: shorten release validation without losing its proof. Goal 2: give customer work independent gate capacity. Initial aweb full/focused path targets 2026-11-13; Cloud follows on 2026-11-16 after its gate owner confirms the entry and inputs. Warm-cache work follows a measured baseline.

## Interface and configuration

`vm-gate run --repo PATH --sha SHA (--stages SET | --command COMMAND) [--type ccx33|ccx43] [--timeout SECONDS]`, plus `status` and `reap`. A configuration file outside the repository supplies provider location, snapshot, owner, state/evidence roots and credential-file location. No operator hostname, address, project identifier, token path or credential enters source. Token access stays in the existing preflight reader, selected through `HCLOUD_TOKEN_FILE`; only the provider client receives its value. Child environments are constructed explicitly.

## Source and execution

Every locally checkable precondition runs before credential access or allocation: refs/SHA, requirements versus the recorded snapshot manifest, command syntax and configuration. Repository-declared lint/format checks run locally on an isolated exact checkout without containers, before token access; their pass lines enter summary.json and the VM checks stage is unchanged. This prevents bootstrap errors from costing a VM. Source admission is for trusted team checkouts: their lint/format make targets execute locally as the operator and can read files that account can read. The scrubbed environment and Docker shim do not sandbox untrusted source. Before spending, require the exact commit, a clean checkout and usable local origin/main/tags; refresh origin locally and record its OID plus the real ancestry result. Build a bundle containing those refs and the selected SHA without exporting Git credentials. The VM recreates a frozen local bare origin. An unlanded SHA is labelled branch qualification; its frozen main may point at that SHA only with that scope made explicit. The original real-main OID remains evidence. Explicit `--intent train` reproduces the coordinator’s train: real origin/main must be an ancestor of the merged candidate and remain unchanged through qualification. The train uses all five stages in the coordinator’s command. Branch intent never claims that it establishes real-main ancestry.

A repository adapter derives host requirements from the selected bytes, checks installed versions/hashes and commands, and refuses mismatch with tool/required/observed/SHA. Provisioning is separate from gate execution. The gate enters a readable checkout as UID 1000 in the Docker group, refuses UID 0, and uses GOTOOLCHAIN=local. An aweb full request uses its ordinary entry point; stage subsets use its existing selector, and focused commands run as supplied. Source-derived sizing settings are preserved. Increment (a) implements only aweb. A repository adapter seam is retained for Cloud on November 16; no Cloud adapter code is included now. The Cloud owner and coordinator have confirmed its full test-only engine and exact C1-input contract separately.

## Lifecycle, concurrency and spend

Each run has a UUID, private directory, immutable input manifest and atomic state/summary files protected by its run lock. Provider resources use the distinct `aweb-vm-gate.*` label namespace, carrying run, owner, SHA and expiry. This lets the B1 diagnostic helpers retain their original namespace without either reaper touching the other’s VMs; SSH trust uses the provider server ID. Paginated inventory precedes allocation. Reads have bounded transient retries; mutations are single attempts, uncertain creates reconcile by label, and capacity refusals name the requested type/code without fallback.

A transaction-backed local spend ledger reserves a conservative maximum before create, counts outstanding reservations across processes, then settles observed lifetime rounded by provider billing. Both server and Primary IP rates are read live in EUR; uncertain accepted resources are included in settlement after label reconciliation. The initial cumulative cap is EUR 150 for the first two weeks, seeded with existing lab spend; daily EUR 20 produces a warning. Independent runs use independent VMs. Shared registry/spend operations use database transactions; authoritative gate-ledger operations use locks. Same-tree stage invocations retain the source gate's exclusion semantics, while unrelated trees and focused commands can run concurrently.

Every run reaps expired labelled resources first. Cleanup reconciles labels, deletes exact server/IP/key IDs, and verifies both label and exact-ID absence. It runs independently of evidence transfer. Expiry includes bounded setup, the full command timeout, evidence pull, teardown and a margin. Each long step receives the remaining phase deadline; a delayed gate refuses before starting if its full timeout would cross completion expiry. Reaping malformed expiry labels reports infrastructure failure while continuing unrelated valid expired runs. The reaper is also callable independently and must recover a controller killed with SIGKILL; no trap can substitute for that proof.

## Results and authoritative ledgers

Retain full logs, the source gate's summary.tsv, memory samples, provider receipts and ledger snapshot; publish summary.json with source/real-main scope, requested work, stage times/status, gate exit, infrastructure classification, memory, cost and resource IDs/times. Return the gate's exit code; infrastructure failure uses a documented distinct result and never becomes a green gate.

Do not replace an authoritative TSV with a concurrent snapshot. Preserve all failure rows and gate logs. Proposed aweb transport: snapshot under the source tree lease, run with that snapshot, then append only observed new rows under the canonical writer lock, retaining immutable per-run originals. A failed-tree guard remains binding; no automatic failure-row removal. Cloud ledger import/combined C4 verdict remains an owner decision before Cloud rollout. Raw test archives remain local/operator-only.

## Snapshot maintenance in increment (a)

`vm-gate snapshot --sha SHA` derives the requested pins, builds from the current configured snapshot, installs only the required tools, seals a new labelled snapshot and verifies its host contract on a separate restored VM. A stable shared config lease protects runs and an exclusive lease protects rebuild/publish. Snapshot storage gets an explicitly reported conservative fourteen-day allowance in the spend cap. Config replacement is atomic and locked; the old snapshot is deleted only after restore verification. A failure preserves the old config/image and reports any new image for reconciliation. Snapshot operations share the spend/reservation ledger and expiry cleanup. `run` pin refusal prints the exact snapshot command to repair it.

## Verification and review

SQLite is the sole registry/spend database. One exit-code module documents gate-code passthrough plus reserved refusal and infrastructure codes; summary.json always states infrastructure classification, and infrastructure cannot exit zero. Test first with fake provider/SSH boundaries: ancestry/bundle refs, source-derived mismatch and UID controls, bounded reads, uncertain creates, capacity refusal, exact-ID cleanup, distinct exits, atomic concurrent reservations and expiry. Real-provider tests require an explicit opt-in and their own small spend ceiling. Run parallel and SIGKILL/reaper acceptance once each on real Hetzner, retain IDs/costs and demonstrate the next invocation cleans the expired killed run. Athena reviews implementation; testing-servers reviews this design. No warm caches or Cloud qualification is claimed by the first aweb increment.
