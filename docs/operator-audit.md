# Operator audit

The OSS server records role publication, repo deletion and app installation in
the existing `audit_log`. The embedding host supplies its own authorization policy; a team
certificate proves membership and key possession, not a Cloud owner/admin human
role. Cloud applies that policy before the mounted OSS route. Standalone OSS
retains its existing certificate-authorized operations.

Migration `023_operator_audit.sql` adds nullable actor fields, so older audit
writers and historical rows remain valid. Records contain team, action, target,
outcome, database server time, request UUID and verified-context actor metadata.
They contain no bodies, playbooks, credential headers or free-form details.
Certificate `actor_did_aw` is a controller assertion; it is not an independent
AWID identity verification.

## Public embedding interface

```python
from aweb.audit import AuditActor, record_coordination_audit

actor = AuditActor(
    team_id=verified_team_id,
    principal_type="k",
    auth_mode="api_key",
    user_id=database_verified_key_owner_user_id,
)
request.state.operator_audit_actor = actor
request.state.operator_audit_request_id = server_generated_request_uuid
```

Only trusted authentication code sets these state fields, after checking the
session, key or certificate and database binding. Do not reconstruct them from
caller-controlled proxy headers. Principal type is explicit `u/k/c/m/p`, never
inferred from the actor's human/agent label. Auth mode is one of `team_auth_v1`,
`team_auth_v2`, `session`, `api_key`, `identity_grant`, `internal`. At least one
of `did_key` or `user_id` is required. `did_aw` and `user_id` are optional, as is
`grant_id` except in `identity_grant` mode, where it is required. A grant records
its subject DID and grant UUID, never its session signing key as the actor.
Native certificates and grants use principal `c`; an embedding's already-verified
principal is preserved, including `k` when a key was exchanged for a certificate.

A successful route calls the insert helper inside the same aweb-schema
`pgdbm.TransactionManager` as its mutation. The helper does not begin or commit a
transaction, catch database errors, or perform network I/O. An insert failure
propagates and rolls back the mutation. Repo Redis cleanup runs after SQL commit,
so an audit failure leaves presence intact. An authenticated HTTP refusal is
recorded in a separate transaction after the mutation transaction rolls back.
Unverified credentials cannot establish an actor and produce no attributed row.
Grants remain refused on these routes; verification only establishes whose
refusal to record. This grants no additional operation scope.

Cloud's early verified-context refusal never enters the OSS handler. It uses
one denial-only transaction and commits before raising its HTTP refusal:

```python
async with aweb_manager.transaction() as tx:
    await record_coordination_audit(
        tx, actor=actor, action="roles.reset", target=f"roles:{actor.team_id}",
        outcome="denied", request_id=server_generated_request_uuid,
    )
```

The helper writes `clock_timestamp()` into the existing `created_at`, action
into `event_type`, target into `resource`, and leaves `details` empty. The new
columns are `actor_did_key`, `actor_did_aw`, `actor_user_id`, `principal_type`,
`auth_mode`, `outcome`, `request_id`, and `actor_grant_id`. Outcomes are `success`
or `denied`. Each handled success or authenticated refusal writes exactly one
row; an audit insert failure cannot count as a successful audited operation.

| Route | Action | Target |
| --- | --- | --- |
| POST /v1/roles | roles.create | roles:&lt;team_id&gt; |
| POST /v1/roles/{id}/activate | roles.activate | roles:&lt;version_uuid&gt; |
| POST /v1/roles/reset | roles.reset | roles:&lt;team_id&gt; |
| POST /v1/roles/deactivate | roles.deactivate | roles:&lt;team_id&gt; |
| DELETE /v1/repos/{id} | repos.delete | repo:&lt;repo_uuid&gt; |
| POST /v1/apps/install | apps.install | app:&lt;app_id&gt; |

Invalid UUID route values use the fixed `roles:invalid` or `repo:invalid` target,
and an app id that is not a valid app id uses `app:invalid`;
raw paths, queries and payloads are never stored as targets. Request UUIDs are
generated by the server if the embedding has not supplied one. There is no audit
viewer or public audit read endpoint in this change.
