Three traps that each produced a confident result about the wrong code.

- **Queued runs.** During a feature freeze, deferred runs executed against a
  committed head plus an uncommitted patch made after queueing. The results were
  evidence for that working tree, not for the commit offered for review. A
  commit label in a wrapper or a mail cannot bind later filesystem reads.
- **Reverting from HEAD.** A mutation loop that reverted each mutation with
  `git checkout -- <file>` restored the last commit, not the pre-mutation file,
  and silently wiped uncommitted work. Later mutations then "failed to apply"
  while still looking like measurements; only the patch assertions caught it.
- **Stale bytecode.** CPython's default pyc check compares source mtime (one
  second resolution) and size. Two same-length mutations within one second
  reused the previous mutation's bytecode, so the second mutation went red for
  the first mutation's guard. A red count alone hid it.

# How to apply

- Choose the evidence boundary before queueing: keep the tested tree unchanged
  until the run ends (a clean-tree pinned runner), or report the result against
  the exact working patch.
- Mutate only a committed baseline, or save and restore the exact pre-mutation
  bytes; have each mutation assert its target text occurs exactly once so a
  vanished target is loud.
- Delete the mutated module's generated bytecode before each mutated run and
  after restoring the source.
- Predict which assertions each mutation should fail and match them against
  the actual failures.

These refine [a harness must be shown to fail](/aweb-expert/lessons/a-harness-must-be-shown-to-fail.md):
a valid detector is still no experiment if it ran other bytes than claimed.
