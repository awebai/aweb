title: Verify migration as an operating contract
description: A package upgrade does not prove that the successor can consume its knowledge, receive work and retain the intended authority.
timestamp: 2026-10-01
---

Review migration as several independent outcomes: source declarations,
provider/runtime readiness, accepted knowledge at the selected destination, and a
successor that actually consumes it and receives work. Preserve claims and
historical material until their disposition is evidenced. Remove obsolete active
guidance only after the replacement is established.

Choose the final execution context and durable-state location before staging.
State outside a Git repository may still lie inside a workspace-mode agent's
work scope. Relocation must preserve absolute references in staged proposals and
source descriptors, not merely file bytes. Declare cross-node reads explicitly;
content migration does not infer all intended knowledge relationships.

A no-launch scaffold can register schedules or other resources. Verify source
state and live scheduler state separately; enabled does not prove executed, and
a source's auto=false does not prove a schedule is disabled. Likewise, a retained
identity intended for one standing seat must not become the default for every
concurrent assignment of an expertise soul. Verify recorded spawn custody and
actual successor delivery, rather than inferring either from requested settings.
These distinctions arose repeatedly in the September–October 2026 migrations.
