## The rule that broke us, and the rule that replaced it

`.claude/skills/cross-repo-change/SKILL.md` said *"Do NOT accept both old and
new formats during transition when both sides deploy atomically. Pick one
format."* Correct for aweb↔aweb-cloud, which ship in one Docker image.
**Catastrophic for published clients, which never deploy atomically with
anything** — a running agent keeps its loaded module until it *restarts*.

A chat mark-read change made `message_ids` required and explicitly rejected
`up_to_message_id`. Every published client sent the old field. Deploying it
would have broken every client in the world. **The process was not ignored — it
was followed.**

Fixed at `e1352042`: the skill now opens with a shippability section — a
released client is a permanent constraint; additive by default; narrowing
requires naming every consumer and proving each deploys atomically; removal is
a separate change gated on *measuring* nobody sends the old shape. The old
principle and anti-pattern are now explicitly scoped to the cloud boundary with
"do not generalise it."

## The original incident, in one paragraph

Channel 1.5.2 shipped with `mailAcknowledgment: "manual"` — it presented mail
and never marked it read, so the server re-announced the backlog on every
connect. One option flip. Fixed in 1.6.0, published 2026-07-25 — and **two days
later 25 of 26 processes were still running 1.5.2**, because a running process
keeps its loaded module until restart. The fix was correct, published, and
irrelevant. Everything else that night was diagnosis being confidently wrong.

## Open, with honest status

- **`aapb` P0 — memory leak.** ~50–60 MB/hour, 2 GB ceiling every ~30h, then
  restarts that kill every SSE stream. **Per-client**: ~5–9 MB/day/agent, so it
  scales with fleet size — a *scaling ceiling*, not a regression. **A deploy
  resets it and buys ~30 quiet hours; quiet is not a fix.** Juan deprioritised
  it: our own agents are the fleet. Ruled out: chat pubsub (closed in a
  `finally`), the database.
- **`aang` P1** — retitled. Stream flapping is *solved* (server restarts from
  `aapb`). The real defect is that **a notification can silently fail to reach
  an agent for an unbounded period with no signal at either end** — measured at
  **21h51m on three P0 assignments**, and the resend didn't rescue it either.
- **`aapd` P2** — `chat_read_receipts` has no FK to `chat_participants` and
  participants are hard-deleted (`left_at` set on 0 of 2,436 rows). Root cause
  of the orphans; `aapc` only makes the backfill tolerate them.
- **`aaoo` P3** — event stream resolves credential DIDs ∪ agent-row DIDs while
  inbox and ack resolve credential DIDs only. Real, not firing. **Do not "fix"
  by narrowing the stream** — that silently stops notifying agents whose row
  DIDs legitimately differ.
- **`aaou` P2** — `register_tools`'s `hosted_encryptor`/`hosted_decryptor`
  parameter *names* are consumed by AC via `inspect.signature`. Renaming them
  silently disables hosted encryption rather than raising.
- **17 processes still on 1.5.2.** Restarting picks up 1.7.0, fixes unacked mail
  *and* moves them off the clobbered global delivery store. Will **not** fix
  flapping. Juan's call — it interrupts agents mid-work, and each floods once as
  its backlog drains. **Say that before restarting** or the drain reads as the
  bug surviving.
- **`aweb-aaop` and `aweb-aaos`** — I closed and overwrote both by running `aw`
  after a `cd`. Reopened; if either was already closed it needs closing again.

## Traps that cost real time, all measured

1. **`aw mail inbox` is unread-only.** "No messages." is indistinguishable from
   being deaf. Use `--show-all` for any reachability check. I made this mistake
   after being warned.
2. **Never write `cd` in a bash block.** Sixth and seventh occurrences tonight,
   and the first that *succeeded silently* — short refs exist on both boards, so
   `aw task update aaop` hit a real stranger's task and printed `✓`. Read the
   ref in the confirmation line.
3. **Count-based greps are blind to condition differences.** Three channel
   builds had *identical* ack call-site counts; they differed in whether a guard
   existed and what the config said. Extract the deciding expression.
4. **`cp` is interactive here** and will hang a command. Use `cat >`.
5. **`git merge -F -` does not read stdin** (unlike `commit -F -`). It fails and
   the subsequent push says "Everything up-to-date."
6. **A tool's progress notice is not proof.** `npm deprecate` prints
   "deprecating…" *before* the request and looks identical on failure. Confirm
   against the service, and poll — CDN lag makes one read meaningless.
7. **Instrument failures outnumbered code defects.** In one investigation: an
   empty inbox meaning acked-not-deaf; a 1.4.12 bundle that cannot emit the
   events being counted; a Render API 1000-line cap silently returning 58
   seconds of a 5-minute window; a transcript double-recording every event; tool
   calls inflating redelivery 170×; a `make` target named as if it verified prod
   that runs on a fresh build DB. **Every one answered the question asked and
   not the question intended.**

## How this team works well

The whole night's value came from **handing findings over with a test
attached** rather than as conclusions. Three separate confident diagnoses were
refuted — ac-coordinator's three-release expand/contract plan, ac-operations'
customer detector, and my own DID-asymmetry mechanism (refuted 8/8 with a
negative control). None cost a code change, because each was testable.

Ask people to **derive** their design decisions rather than confirm them. That
instruction alone killed a wrong rule (`exactly-one`), a wrong spec of mine, and
surfaced a hole in a fallback — all before code existed.

And **verify what fits**, not just what surprises. I escalated
"every customer shares one rate-limit bucket" to Juan as a hard blocker without
checking. It was wrong; the real surface was 13 auth endpoints, and general
traffic keys on `api_key_id`. Escalating someone's finding means owning its
verification.
